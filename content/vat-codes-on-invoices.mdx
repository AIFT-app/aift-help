# VAT Codes on Invoices

A VAT code is not a field someone types. It is **resolved from five elements**, and that resolution happens on an invoice's **Lines & VAT** tab. The elements themselves, and the tables behind them, are in [VAT master data](/vat-master-data); this article is about what happens to them on a real invoice.

## How A Line Gets Coded

Coding runs **after extraction, as part of categorisation**, in the same AI call that picks the category. It is not part of reading the document.

Several things get a say, most specific first:

1. **NAV data**, on a Hungarian invoice. NAV fixes the **rate** and the **calculation method**, nothing else: it carries no product or service classification. The whole code is settled without asking the AI only when exactly one of your active codes carries a matching NAV mapping code; otherwise the product/service question still goes to the model.
2. **A learned correction.** When you have corrected a similar line before, what gets replayed is the **product/service group**, not the code. That is deliberate, so a code learned before a rate change is not applied after it. A match therefore does not skip the AI call: the rate and the method still have to come from somewhere.
3. **A partner default.** "Always sells", on the partner's Rules tab, fixes the product/service group for every line from that supplier and outranks the AI's own guess. It sets that one element and nothing else.
4. **The AI's own reading** of the line.
5. **The workspace default code**, if all of that still leaves the line unresolved. See below.

Two things the article used to promise and the product does not do. A partner with no VAT group is **not** inferred from its country at this point: the country guess happens once, when the counterparty is first created, so the second and every later invoice from an untagged counterparty simply arrives without that element. And the NAV rate is matched to your nearest configured rate within half a percentage point, refusing to choose on a tie, which is a good heuristic rather than a deterministic mapping.

Resolution keys on the **VAT date**. With no VAT date on the invoice it silently uses today's date, which is worth knowing before you wonder why an old invoice took a current code. Only the code's own validity dates are consulted, not the individual elements'.

### The workspace default code

You can set one default VAT code per direction. A line whose elements cannot be fully determined takes it, and the cell then reads the code with a **Default** badge beside it.

It is narrower than a guess. A default that contradicts an element the system did identify is refused, a fully identified line never takes it at all, and an identified partner group that disagrees with the default disqualifies the whole invoice from the fallback.

**A default-coded line counts as coded.** The invoice is export-eligible and shows no "incomplete" warning; what it carries instead is a **VAT: default-coded** marker on the invoice list. Review is advisory by design. When you have looked at them, the toolbar's **VAT coding OK** button clears the flag on all of them at once.

## Reading The VAT Code Cell

Four things you will see:

- **A code, plain.** Resolved and consistent.
- **A code with a Default badge.** The workspace default, review advised.
- **`- missing -`.** Nothing resolved.
- **A code with a warning triangle.** The code is still assigned, but the line's current elements no longer resolve to it. This is not a record of someone overriding the line: a rate change, a partner VAT group change or a VAT date change will all trip it. The assigned code still wins.

The three element dropdowns are only shown inline **while the line is unresolved**. Once a code resolves, the cell reads **Resolved: see Advanced** and they move into the row's **Advanced** expander, which the arrow at the end of the row opens (its tooltip reads **Advanced**). That is the single most confusing behaviour on this screen, and it is deliberate: a finished line takes less room.

Advanced also holds the non-deductible percentage override. Where a non-deductible share has been folded in, the row shows a **Booked** figure underneath, which is the gross treated as net.

## When Nothing Resolves

An un-coded line reads **`- missing -`**, and the invoice picks up a **VAT codes incomplete** marker on the list. You will also see a to-do on the invoice's Overview and an amber dot on the **Lines & VAT** tab. There is no banner on the invoice, whatever you may have been told.

Two ways forward, and they are not the same thing:

- **The `+ Add` link beside the missing code creates a brand-new VAT code** in your master data for that combination of elements. Use it when the combination is genuinely missing from your table.
- **To assign a code you already have**, open the row's **Advanced** expander with the arrow at the end of the row and pick it there.

Two traps worth knowing. An invoice with **no lines at all** reads as complete, because completeness means "no line is missing a code" and there are no lines to check. And **re-extracting a document does not preserve your VAT corrections**: re-extraction deletes the line rows and inserts fresh ones. What is protected is an AI re-run over the existing rows, which leaves anything you set by hand alone.

## Correcting A Code Or An Element

Four moves, each with a different reach:

- **Change an element** on the line, and the code re-resolves from the new combination.
- **Pick a code directly**, and the line's elements are back-filled from that code and marked consistent.
- **Change the partner VAT group**, at the top of the **Lines & VAT** tab. This is an override: left alone it reads "Use partner default" and follows the partner. Changing it re-resolves **every** line on the invoice.
- **Change the VAT date**, in the Dates row on the **Overview** tab. This also re-resolves every line.

The durable home of a partner's VAT group is the partner itself, under **Master data → Partners**. Set it once and every future invoice starts with the right group; the invoice-level override is for the one-off case.

## Fixing A Backlog In One Go

Adding the missing code to your table does not retro-fill the invoices that were waiting for it. The invoice list has a **Re-run VAT coding** action for that.

It only ever fills lines whose code is **missing**: coded lines, anything you set by hand, and categories are never touched. Note that it runs over the **whole workspace** rather than your selection, and it caps at 2000 invoices, so a large backlog takes more than one run.

## Who Can Do This

Correcting VAT on a line needs the **"Edit invoices"** permission, which is firm-side only: a client-side user can never hold it. They still see the Lines & VAT grid in full, read-only, with the dropdowns disabled and the add and toolbar controls hidden.

Among accountants it is a permission rather than a job title, so a custom role or a per-member denial can make the grid read-only for someone on the accounting side too.

## Foreign-Currency VAT

Where the invoice is in a currency other than the workspace's base currency, the row's **Advanced** expander holds a **VAT exchange rate** and the VAT amount in the reporting currency. Editing either recalculates the other, and both reach the Ledger export as their own columns.

These are **what the supplier printed**, recorded for the VAT return. Nothing is converted here: see [Multi-Currency & Exchange Rates](/currency-exchange) for the rates that do convert.

## When The AI Cannot Decide

Unlike a category, a VAT element has no "the AI declined" state. An element it cannot determine is simply left empty, because recording a verdict there would claim one that was never usable. What you see instead is the invoice's confidence dropping, which can be enough to flag it for review.

A company on the small-business exemption is a special case, and two situations there are left uncoded on purpose rather than given a plausible-looking zero rate. See [Small business VAT exemption](/small-business-exemption).
